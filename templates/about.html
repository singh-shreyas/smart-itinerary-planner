About & methodology

How the planner thinks

An Analysis and Design of Algorithms project. It splits a hard, real planning problem into textbook sub-problems, solves each with a classic algorithm, and is honest about where the guarantees stop.

The problem

A tourist has a few days in a city and far more attractions than time. Each attraction has a value (rating, popularity and whether it matches the traveller's interests), a visit duration, an entry fee and opening hours that differ by weekday. Moving between places takes time and money. We must choose which attractions to visit on which day, and in what order, so the plan is worth as much as possible without breaking the daily time window, any opening hours or the budget.

This is the multi-day Orienteering Problem with Time Windows, which is NP-hard: no known algorithm solves it optimally in polynomial time. So we do not claim optimal itineraries. Instead we decompose it into sub-problems that each have a well-understood algorithm: shortest paths, selection, route ordering and scheduling.

Input

City, start date, days, daily window, optional budget, interests, pace, start point, selection strategy.

Hard constraints

Opening windows and last entry on that weekday · back at the start by day end · daily budget · no repeats · only reachable places.

Output

Ordered stops per day with arrive/start/end/leave times, travel legs, costs, and a reason for every left-out attraction.

The pipeline

Dijkstra runs once per city. Then each day goes through select → route → check → repair, in date order.

Scoring and the knapsack model

Where is travel time in the knapsack? Travel depends on the order, which is decided after selection. So each stop's weight is visit + pace buffer + cheapest trip out of it, and the capacity is the day length minus the shortest first ride. Every route leaves each stop exactly once, so these weights can only under-estimate the real day: the knapsack never throws away a set that truly fits. The scheduler then checks the real timeline, and repair fixes optimism.

Discretisation. Weights are rounded up to 10-minute units and the capacity down; fees are rounded up to money units of max(₹10, budget/100). So anything the DP accepts really fits, and the table stays small (≤ ~100 money cells). Greedy and DP receive the identical integer instance, which keeps the comparison fair.

What "optimal" means here. DP is optimal for this rounded knapsack model on each day. 2-opt reaches a local optimum. Held–Karp is exact for travel only, ignores opening hours, and is used on the comparison page as a lower bound. None of this makes the whole multi-day itinerary provably optimal.

Limitations

  • The full problem is NP-hard; select-then-route is a decomposition heuristic and can miss a better combination.
  • Days are planned in date order, so the plan is myopic: an early day may take an attraction a later, more restricted day needed.
  • Composing local links can make a long trip slightly slower than the true direct road time.
  • Fixed visit durations; no queues, security checks, lunch breaks or ticket booking.
  • Activity selection's optimality proof assumes fixed intervals with no travel, so here it is a heuristic.
  • Map lines are straight segments in visit order, not road geometry.
  • Opening hours, fees, ratings and durations are illustrative until verified.
